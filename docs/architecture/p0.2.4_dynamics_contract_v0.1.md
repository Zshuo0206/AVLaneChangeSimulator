# AV Lane Change Simulator
## P0.2.4 Dynamics Contract v0.1

This phase adds a structural Control contract and two pure one-step dynamics
primitives. It preserves the [Phase 0 requirements](../requirements/phase0_requirements_v0.1.md),
[architecture](p0.2_architecture_v0.1.md),
[VehicleState contract](p0.2.2_data_model_contract_v0.1.md),
[TSC-01/02/03](p0.2.2b_theory_to_software_contract_v0.1.md) and
[Scenario / TheoryModelParameters](p0.2.3_scenario_contract_v0.1.md).
Existing contracts, creators, validators and tests remain unchanged.

## Control data contract

```matlab
control = avlc.model.createControl(ax, ay);
avlc.model.validateControl(control);
```

The creator returns a scalar struct with exactly `ax` and `ay`, acceleration
commands in m/s^2. Both inputs must be numeric, real, scalar and finite;
logical values are rejected. Both signs and zero are structurally valid.
Inputs are validated before conversion to double. The validator requires both
fields, accepts compatible extra fields, returns no output on success and
does not modify input. Invalid data raises `AVLC:InvalidControl`.

The generic creator/validator has no A/B/C bound policy. Structural validity
of Control and admissibility for a particular physical model are different
responsibilities. There is no clipping, replacement or default insertion.

## Shared step inputs and outputs

Both primitives reuse `avlc.model.validateVehicleState(state)`. They accept
positive finite real numeric scalar `dt` in seconds; invalid values raise
`AVLC:InvalidTimeStep`. Integer time steps are accepted. There is no
SimulationConfig dependency, timestep framework, final-time policy or time
vector in these functions.

Required input numbers are converted to double before propagation and bound
arithmetic, including negation of braking/lateral limits. This avoids integer
saturation and unsigned-negation errors for otherwise valid data contracts.
Inputs are not mutated. Each result is created through
`avlc.model.createVehicleState` and contains exactly the existing six fields
`x, y, vx, vy, ax, ay`, stored as doubles. Optional input metadata is not copied
into the new result. A returned state always passes its existing validator.
If floating-point arithmetic produces nonfinite output, the VehicleState
creator raises `AVLC:InvalidVehicleState` instead of returning invalid state.

Positions are vehicle geometric centers in m; velocities use m/s. `+x` is
forward and `+y` points toward Target Lane. No Road or Vehicle is needed for
one-step propagation. Extra compatible fields in nested inputs are accepted
by the existing validators, but have no propagation meaning.

## Constant-velocity primitive

```matlab
nextState = avlc.dynamics.stepConstantVelocity(state, dt);
```

One exact constant-velocity step is:

```text
x_next  = x + vx * dt
y_next  = y + vy * dt
vx_next = vx
vy_next = vy
ax_next = 0
ay_next = 0
```

Input `state.ax` and `state.ay` are validated snapshots but never affect
propagation. Arbitrary valid signs of `vx` and `vy` are allowed; `vy==0` is
not required. This is a general kinematic primitive. Using it for surrounding
vehicles of the frozen reduced theory will be a later orchestration decision,
not a role binding introduced here.

## Ego double-integrator primitive

```matlab
nextState = avlc.dynamics.stepEgoDoubleIntegrator( ...
    state, control, theoryParameters, dt);
```

The primitive reuses VehicleState, Control and TheoryModelParameters
validators. Invalid nested inputs retain their respective identifiers:
`AVLC:InvalidVehicleState`, `AVLC:InvalidControl`, or
`AVLC:InvalidTheoryModelParameters`. It then validates `dt` and checks bounds.

```text
A = theoryParameters.maxLateralAccel
B = theoryParameters.maxLongitudinalBrake
C = theoryParameters.maxLongitudinalAccel

-B <= control.ax <= C
-A <= control.ay <= A
```

All endpoints are valid. Any strict violation raises
`AVLC:ControlOutOfBounds`; controls are never clamped. No numerical tolerance
widens the admissible interval. Overshoot and safety-clearance parameters
retain their data-contract validation but are not used for propagation.

Control is held constant for the step. With `ax=control.ax` and
`ay=control.ay`, the analytical zero-order-hold update is:

```text
x_next  = x + vx*dt + 0.5*ax*dt^2
vx_next = vx + ax*dt
y_next  = y + vy*dt + 0.5*ay*dt^2
vy_next = vy + ay*dt
nextState.ax = control.ax
nextState.ay = control.ay
```

The acceleration displacement is evaluated as `(0.5*a*dt)*dt`, an algebraic
form of the specified expression without separately squaring `dt`.
The update is exact for constant acceleration over the step, subject to
ordinary double-precision rounding. There is no Euler position approximation,
ODE solver, Runge-Kutta scheme or integrator selection.

## TSC-03 and physical responsibility

`state.ax/state.ay` are **not theoretical dynamic states**. They record current
or most recently applied acceleration for diagnostics, logging and replay.
They have no acceleration derivative, jerk control or independent evolution.
`control.ax/control.ay` are **authoritative during Ego propagation**. Even
contradictory finite input snapshots must not change the new trajectory.

Physical Ego dynamics permits negative `vx`, negative `vy` and a step crossing
from positive to negative `vy`. The progressive shared-prefix constraint
`w>=0` is a future evaluator responsibility and is not imposed by Dynamics.
This preserves the ability to represent later abort execution.

Neither primitive checks gaps, vehicle ordering, lane occupancy, collision,
safety clearances, completion or abort feasibility, or any capability theory.
No Theory State Builder or gap/relative-velocity mapping is implemented.

## Binding and phase boundary

There is no role-to-dynamics dispatcher, factory or model assignment yet.
`vehicle.dynamics.type="UNASSIGNED"` and its parameter container are unchanged.
These primitives do not receive or edit Vehicle objects or Scenario data.
The Simulation Engine, role/model binding, time vectors and loop orchestration
remain future work. `runSimulation` and `evaluateCapability` remain their
original explicit placeholders.

This phase adds no surrounding constant-acceleration/piecewise model,
trajectory planner, Scenario preset, event execution, Theory State Builder,
capability evaluator, safety checker, visualization, GUI or persistence.
P0.2.5 is not part of this task.

## Verification

Function-based tests cover Control normalization/validation, analytical motion,
stationary and negative-velocity cases, exact and immediately exceeded control
bounds, contradictory snapshots, lateral zero crossing, integer arithmetic,
input immutability, output schemas, invalid nested inputs/timesteps and
rejection of nonfinite output. Floating-point expected values use tolerances.

```matlab
run("examples/check_project_structure.m")
addpath("src")
results = runtests("tests");

```
