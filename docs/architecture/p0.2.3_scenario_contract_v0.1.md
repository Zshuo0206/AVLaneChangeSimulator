# AV Lane Change Simulator
## P0.2.3 Scenario Contract v0.1

This contract implements structural experiment data only. It supplements the
[Phase 0 requirements](../requirements/phase0_requirements_v0.1.md),
[P0.2 architecture](p0.2_architecture_v0.1.md),
[P0.2.2 data models](p0.2.2_data_model_contract_v0.1.md), and authoritative
[P0.2.2b theory-to-software mapping](p0.2.2b_theory_to_software_contract_v0.1.md).
Existing contracts and P0.2.2 behavior are unchanged.

## TheoryModelParameters

```matlab
params = avlc.model.createTheoryModelParameters( ...
    maxLateralAccel, maxLongitudinalBrake, maxLongitudinalAccel, ...
    targetOvershoot, frontSafetyClearance, ...
    rearOriginalSafetyClearance, rearTargetSafetyClearance);
avlc.model.validateTheoryModelParameters(params);
```

The creator returns an ordinary scalar struct with exactly these seven fields:

| Field | Frozen meaning | SI unit | Constraint |
| --- | --- | --- | --- |
| `maxLateralAccel` | A, lateral acceleration magnitude | m/s^2 | >0 |
| `maxLongitudinalBrake` | B, longitudinal braking magnitude | m/s^2 | >0 |
| `maxLongitudinalAccel` | C, longitudinal acceleration magnitude | m/s^2 | >0 |
| `targetOvershoot` | delta_T_bar, completion overshoot allowance | m | >=0 |
| `frontSafetyClearance` | Required EGO / FO bumper clearance | m | >=0 |
| `rearOriginalSafetyClearance` | Required EGO / RO bumper clearance | m | >=0 |
| `rearTargetSafetyClearance` | Required EGO / RT bumper clearance | m | >=0 |

Every required value is numeric, real, scalar and finite. The creator validates
before converting to double; logicals are not numeric inputs. The validator
accepts valid numeric classes without normalization and returns no output on
success. Invalid data raises `AVLC:InvalidTheoryModelParameters`. Missing fields,
empty/nonscalar model structs, invalid signs, NaN, Inf, complex, nonscalar and
nonnumeric values fail explicitly. No clipping, replacement or defaults occur.
Compatible additional fields are allowed by the validator, but are not emitted
by the creator and do not redefine the documented constants.

VehicleState, Road, vehicle geometry, initial conditions, simulation `dt` and
`endTime`, derived capability quantities and solver settings are not part of
this model. Vehicle lengths remain in Vehicle; Road owns geometry;
SimulationConfig owns numerical simulation configuration.

## Scenario

```matlab
scenario = avlc.scenario.createScenario( ...
    name, description, road, theoryParameters, ego, fo, ro, rt);
avlc.scenario.validateScenario(scenario);
```

The creator emits exactly these six top-level fields and four vehicle slots:

```text
scenario.name
scenario.description
scenario.road
scenario.theoryParameters
scenario.vehicles.EGO
scenario.vehicles.FO
scenario.vehicles.RO
scenario.vehicles.RT
scenario.events
```

`name` is a nonempty text scalar. `description` is a text scalar and may be
empty. Both accept nonmissing MATLAB string scalars or character vectors,
including column vectors, and the creator stores them as string scalars.
String arrays, character matrices and non-text data are rejected. Text is not
trimmed, and no name is invented.

Scenario and its `vehicles` container must be scalar structs. Every documented
field is required. Existing Road, TheoryModelParameters and Vehicle validators
are reused; no duplicate nested validation rules are introduced. Nested input
objects are retained unchanged, including valid numeric/text representations
and compatible metadata. Scenario does not normalize nested data in place.

### Roles and IDs

Each authoritative slot must contain a valid Vehicle whose internal role is
exactly the slot name: EGO, FO, RO or RT. Case is significant at this Scenario
boundary; the Vehicle creator is responsible for canonical uppercase roles.
The standalone Vehicle validator's existing case-insensitive behavior remains
unchanged. A wrong-slot, swapped or corrupted role is rejected; no repair or
reordering takes place.

The four Vehicle IDs must be pairwise distinct using exact normalized string
equality. Character-vector IDs are compared as string scalars without changing
the stored input. Matching is case-sensitive: `"ego01"` and `"EGO01"` are distinct.

### Events and forward compatibility

The creator accepts no event argument and initializes `scenario.events` to
`struct([])`. The validator accepts only empty struct arrays; numeric `[]`, a
scalar `struct()` and nonempty event data are rejected. There is no event schema,
scheduler, trigger interpretation or event behavior in P0.2.3.

Validators accept compatible extra fields in TheoryModelParameters, Scenario
and `scenario.vehicles`. Such fields do not become required creator outputs.
Extra vehicle fields do not become authoritative Phase 0 participants and are
not used in role or ID validation; the required four participants still must
be valid. No additional vehicle role is introduced.

### Error boundary

Invalid Scenario data raises `AVLC:InvalidScenario`. When Road,
theoryParameters or any required Vehicle fails its nested validator, the
Scenario error message identifies the object and retains the original MATLAB
exception through `addCause`. Nested identifiers are not leaked as the public
Scenario error identifier. Validation returns normally, with no output or
mutation, for a valid Scenario.

## Structural validity is not theoretical safety

Scenario is a structural experiment definition. Validation does not check or
derive traffic safety, collision freedom, minimum gaps, lane-change feasibility,
abort/completion capability, dual-option capability, progressive feasibility
or maneuver-freedom horizon. No vehicle longitudinal ordering, lane-center
occupancy, positive speed, velocity ordering or theory acceleration bound is
enforced. Structurally valid unsafe, boundary, degenerate and unusual states
remain valid research inputs, including those with negative future safety gaps.

Vehicle `(x,y)` still denotes its geometric center in m. `+x` is forward and
`+y` points from Original Lane to Target Lane. State velocities use m/s and
acceleration snapshots use m/s^2; Road geometry and display limits use m.
`VehicleState.ax/ay` remain current / most recently applied acceleration
snapshots for recording and visualization. They are not theoretical dynamic
states, control commands or derivatives. No control behavior is introduced.

## Frozen mappings: documentation only

These relations preserve P0.2.2b. They are not implemented in this phase.
Let `L_i` be Vehicle length and `v_i` longitudinal `state.vx`.

```text
d_F = (L_EGO + L_FO)/2 + frontSafetyClearance
d_R = (L_EGO + L_RO)/2 + rearOriginalSafetyClearance
d_T = (L_EGO + L_RT)/2 + rearTargetSafetyClearance

g_F = x_FO - x_EGO - (L_EGO + L_FO)/2 - frontSafetyClearance
g_R = x_EGO - x_RO - (L_EGO + L_RO)/2 - rearOriginalSafetyClearance
g_T = x_EGO - x_RT - (L_EGO + L_RT)/2 - rearTargetSafetyClearance

W = road.targetLaneCenterY = road.laneWidth
road.originalLaneCenterY = 0
K = B + C

c_R = v_RO - v_EGO
c_F = v_EGO - v_FO
c_T = v_RT - v_EGO
```

Positive `c` means the corresponding safety gap is closing. Safety clearances
are bumper distances, not the finite-branch discriminants `s_F`, `s_R`, `s_T`.
`W` comes only from Road. `W`, `d_F/d_R/d_T`, `K`, `g_R/g_F/g_T` and
`c_R/c_F/c_T` are future derived values; neither creator calculates or stores
them, and they must not be manually duplicated in Scenario or its parameters.

```text
Physical Scenario
       |
       v
future Theory State Builder
       |
       v
z = (y,w,g_R,c_R,g_F,c_F,g_T,c_T)
```

The Theory State Builder is **not implemented** in P0.2.3. It is a future
adapter, not an authoritative dynamics model. CapabilityEvaluator and all
analytical capability algorithms remain unimplemented. The frozen reduced
evaluator's assumptions remain separate from broader simulation data validity.

## Verification and scope

The new function-based tests cover parameter schema/normalization/boundaries,
Scenario schema/text, nested validation and exception causes, role-slot checks,
all six duplicate-ID pairs, case-sensitive IDs, empty event reservation,
immutability, extra-field compatibility and acceptance of unusual/unsafe states.
All existing tests must continue to pass unchanged. From the project root:

```matlab
run("examples/check_project_structure.m")
addpath("src")
results = runtests("tests");
assert(~isempty(results) && all([results.Passed]))
```

No Scenario presets, Theory State Builder, gap or relative-speed calculation,
Dynamics, Control struct, Simulation Engine, time vector, SimulationResult,
capability evaluation, event behavior, safety test, collision checking,
visualization, animation, GUI or IO persistence is implemented by this step.
P0.2.4 and later phases are outside this task.
