# AV Lane Change Simulator
## P0.2.2 Data Model Contract v0.1

This document records the implemented Phase 0 fundamental data contracts.
It refines the [Phase 0 requirements](../requirements/phase0_requirements_v0.1.md)
and [P0.2 architecture](p0.2_architecture_v0.1.md) for P0.2.2 only.
Scenario, Dynamics, Simulation Engine, analysis calculations, results,
visualization, IO and GUI are not implemented by this step.

## Representation and validation policy

All four models are ordinary scalar MATLAB structs. No `classdef`, external
dependencies, inheritance, or general-purpose validation framework is used.
Only `src` needs to be added to the MATLAB path.

Creators validate their inputs through the corresponding validator before
normalizing the documented fields. Every returned object satisfies its
validator. Creators produce only the documented fields at their own schema
levels; `createVehicle` retains the supplied, validated `initialState`,
including any compatible additional fields already present in that state.

Validators require every documented field, accept additional fields, return
no output on success, and do not mutate, repair, clip or insert defaults.
They accept valid numeric MATLAB classes, including integers and single
precision, without requiring pre-normalization to double. A valid numeric
scalar is numeric, real, scalar and finite. Logical values are not accepted
as numeric data. Empty struct arrays and nonscalar structs used as model
objects, geometry containers or dynamics containers fail.
Invalid contract data raises the model-specific error identifier below.

Text inputs for Vehicle may be nonmissing string scalars or character
vectors, including column character vectors. Text matrices, string arrays
and missing string values are rejected. No text is trimmed and no IDs are
invented. Role matching is case-insensitive; creator output uses uppercase.

## Coordinates and units

- `+x` is the road forward direction.
- `+y` points from the original lane toward the target lane.
- Vehicle `(x,y)` is the geometric center, not an axle or bumper reference.
- Positions, dimensions, lane width and display range use m.
- Velocities use m/s, accelerations use m/s^2, and times use s.
- Internal units remain SI; unit conversions belong to later display code.

## VehicleState

```matlab
state = avlc.model.createVehicleState(x, y, vx, vy, ax, ay);
avlc.model.validateVehicleState(state);
```

| Field | Meaning | Creator storage |
| --- | --- | --- |
| `x` | Longitudinal geometric-center position, m | double scalar |
| `y` | Lateral geometric-center position, m | double scalar |
| `vx` | Longitudinal velocity, m/s | double scalar |
| `vy` | Lateral velocity, m/s | double scalar |
| `ax` | Longitudinal acceleration, m/s^2 | double scalar |
| `ay` | Lateral acceleration, m/s^2 | double scalar |

All six required fields must be finite real numeric scalars, representing
`X_i = [x_i, y_i, vx_i, vy_i, ax_i, ay_i]^T`. Negative values are valid.
No velocity sign constraint or vehicle-specific acceleration bound is imposed.
Invalid input raises `AVLC:InvalidVehicleState`.

## Vehicle

```matlab
vehicle = avlc.model.createVehicle(id, role, length, width, initialState);
avlc.model.validateVehicle(vehicle);
```

| Field | Contract / creator storage |
| --- | --- |
| `id` | Nonempty text scalar; stored as string scalar |
| `role` | Exactly EGO, FO, RO or RT after uppercasing; stored as uppercase string scalar |
| `geometry.length` | Positive finite real numeric scalar in m; stored as double |
| `geometry.width` | Positive finite real numeric scalar in m; stored as double |
| `initialState` | Must pass `validateVehicleState`; retained as supplied |
| `dynamics.type` | Text scalar; creator sets string `"UNASSIGNED"` |
| `dynamics.parameters` | Struct; creator sets scalar `struct()` with no fields |

`geometry` and `dynamics` are scalar structs. The creator emits exactly the
listed top-level fields and the two listed fields in each of these containers.
It does not create, assign or run any dynamics model.

The validator reuses `validateVehicleState`. Invalid nested state data is
reported at the public Vehicle boundary as `AVLC:InvalidVehicle`, with a
message identifying `initialState`. Other invalid Vehicle contract data uses
the same identifier.

The dynamics validator checks only the container shape, text type and struct
parameters. It does not interpret model names or parameter contents. Empty
text is structurally valid for `dynamics.type`, and struct arrays are permitted
for `dynamics.parameters`; neither establishes a usable dynamics model.
The creator always supplies the canonical unassigned placeholder above.

Vehicle ID uniqueness and Vehicle role uniqueness are future Scenario
responsibilities. Repeated calls with the same ID or role are valid individual
Vehicle constructions. Additional roles such as FT, NPC, LEAD and FOLLOWER are
not accepted in P0.2.2.

## Road

```matlab
road = avlc.model.createRoad(laneWidth, displayXRange);
avlc.model.validateRoad(road);
```

| Field | Phase 0 invariant / creator storage |
| --- | --- |
| `numLanes` | Exactly 2; double scalar |
| `laneWidth` | Positive finite real numeric scalar in m; stored as double |
| `originalLaneCenterY` | Exactly 0 m; double scalar |
| `targetLaneCenterY` | Equal to `laneWidth` in m; double scalar |
| `displayXRange` | Two finite real numeric limits with `xMin < xMax`; stored as 1-by-2 double row |

The road is restricted to two straight parallel lanes. Original Lane center
is `y=0` and Target Lane center is `y=laneWidth`. There is no configurable
offset, curvature, heading, lane ID, or map object.

The validator accepts row or column display vectors. Target-center consistency
uses `abs(targetLaneCenterY - laneWidth) <= 1e-10 * laneWidth`, evaluated as
doubles. The original-lane origin and lane count are exact fixed invariants.
No minimum positive lane width is imposed. The display range is visualization
metadata and does not constrain simulation physics or vehicle positions.
Invalid input raises `AVLC:InvalidRoad`.

## SimulationConfig

```matlab
config = avlc.model.createSimulationConfig(dt, endTime);
avlc.model.validateSimulationConfig(config);
```

| Field | Contract / creator default |
| --- | --- |
| `dt` | Positive finite real numeric scalar in s; stored as double |
| `endTime` | Positive finite real numeric scalar in s; stored as double |
| `integrationMethod` | Exactly `"fixed-step"`; creator stores a string scalar |
| `storeEveryStep` | Scalar logical; creator sets `true` |
| `enableCapabilityEvaluation` | Scalar logical; creator sets `false` |

The validator also accepts the character row `'fixed-step'`. It rejects any
other integration-method name and rejects numeric 0/1 as logical flags.
Both logical values are structurally valid for each flag. In particular,
`enableCapabilityEvaluation=true` passes validation without calling or
implementing CapabilityEvaluator. No additional integration algorithm is
introduced here.

No integral `endTime/dt` requirement, `dt <= endTime` requirement, time vector,
integration step or final-time rounding policy is imposed. The final-step
policy belongs to the future Simulation Engine. Invalid input raises
`AVLC:InvalidSimulationConfig`.

## Responsibility boundaries

| Concern | Owner |
| --- | --- |
| Required fields, scalar data validity, normalization | P0.2.2 creators and validators |
| Vehicle ID uniqueness | Future Scenario validation |
| Vehicle role uniqueness | Future Scenario validation |
| Dynamics interpretation and parameters | Future P0.2.4 |
| `endTime/dt` final-step policy | Future Simulation Engine |
| State propagation and numerical integration | Future Dynamics / Simulation Engine |
| Capability evaluation | Reserved independent Analysis interface |

This contract does not implement Scenario, state propagation, gaps, relative
velocities, events, SimulationResult, GUI, or theoretical capability formulas.
The existing `runSimulation` and `evaluateCapability` placeholders retain
their original errors and behavior.

## Verification

From the project root in MATLAB R2024b:

```matlab
addpath("src")
run("examples/check_project_structure.m")
results = runtests("tests");
assert(~isempty(results) && all([results.Passed]), "Data-model tests failed.")
```

The four function-based test files cover valid construction, exact creator
schemas, type normalization, required fields, malformed containers, numeric
edge cases, nested validation, read-only extra-field compatibility, road
geometry consistency and configuration defaults. Floating-point expectations
use explicit tolerances. They perform no simulation and require no GUI.
