# AV Lane Change Simulator
## P0.2.2b Theory-to-Software Contract v0.1

Status: **Frozen**. This is a documentation and governance baseline, not a
MATLAB implementation or a replacement for the frozen analytical theory.

This contract supplements the repository-controlled
[Phase 0 requirements](../requirements/phase0_requirements_v0.1.md),
[P0.2 architecture](p0.2_architecture_v0.1.md), and
[P0.2.2 data-model contract](p0.2.2_data_model_contract_v0.1.md).
Existing P0.2.2 fields, creators, validators and behavior remain unchanged.

In the notation below, analytical `E` maps to software role `EGO`;
`x_i` is the vehicle geometric-center longitudinal coordinate, `v_i` maps
to longitudinal velocity `state.vx`, and `L_i` maps to `vehicle.geometry.length`.
The reduced lateral quantities `y` and `w` map to EGO `state.y` and `state.vy`.
All quantities retain the frozen SI units and coordinate conventions.

## TSC-01 — Safety-distance mapping

The frozen analytical theory uses longitudinal quantities:

```text
d_F
d_R
d_T
```

inside:

```text
g_F = x_FO - x_E - d_F
g_R = x_E - x_RO - d_R
g_T = x_E - x_RT - d_T
```

The simulator uses vehicle geometric-center coordinates.

Therefore the theory distances are mapped from physical vehicle geometry and bumper-to-bumper safety clearances as:

```text
d_F = (L_E + L_FO)/2 + delta_F_clearance
d_R = (L_E + L_RO)/2 + delta_R_clearance
d_T = (L_E + L_RT)/2 + delta_T_clearance
```

Equivalent software interpretation:

```text
geometric bumper gap
-
required bumper safety clearance
=
theory gap state g
```

For example:

```text
g_F =
x_FO - x_E
- (L_E + L_FO)/2
- delta_F_clearance
```

The same convention applies to RO and RT.

Important:

Do not use symbols:

```text
s_F
s_R
s_T
```

for safety clearances because the frozen theory already uses those symbols for finite-branch discriminant quantities.

Recommended descriptive software terminology:

```text
frontSafetyClearance
rearOriginalSafetyClearance
rearTargetSafetyClearance
```

This mapping is a software bridge.

It does not modify the frozen analytical definitions.

## TSC-02 — Lateral-reference mapping

Freeze:

```text
original lane reference:
y_O = 0
```

The analytical target coordinate is:

```text
W = y_target - y_original
```

For the current Phase 0 Road model:

```text
road.originalLaneCenterY = 0
road.targetLaneCenterY   = road.laneWidth
```

therefore:

```text
W = road.targetLaneCenterY
  = road.laneWidth
```

during Phase 0.

`W` must NOT become an independent user-configurable duplicate of the Road geometry.

Road geometry is the authoritative software source.

The future theory adapter derives `W` from Road.

The analytical stable completion state remains:

```text
(y,w) = (W,0)
```

and the completion overshoot envelope remains conceptually:

```text
y <= W + targetOvershoot
```

where the overshoot parameter remains a separate theory/model parameter.

## TSC-03 — Acceleration semantics

Freeze the distinction between:

```text
dynamic state
```

and:

```text
control input
```

The frozen theory uses controls:

```text
u = (a_x, a_y)
```

with:

```text
a_x in [-B,C]
a_y in [-A,A]
```

Acceleration is NOT a theoretical dynamic state.

The existing Phase 0 VehicleState fields:

```text
state.ax
state.ay
```

must be interpreted as:

```text
current / most recently applied acceleration snapshot
```

for:

```text
logging
visualization
trajectory recording
diagnostics
```

They do NOT introduce dynamics of the form:

```text
dot(a_x) = ...
dot(a_y) = ...
```

and must never convert the frozen double-integrator model into a triple-integrator model.

Future Dynamics code must receive authoritative acceleration through a separate control input conceptually equivalent to:

```text
control.ax
control.ay
```

State propagation must not treat:

```text
currentState.ax
currentState.ay
```

as the authoritative next-step control command.

After applying the current control, the resulting VehicleState may record that applied acceleration in:

```text
nextState.ax
nextState.ay
```

for logging purposes.

P0.2.2b records this behavior as a future contract only; it does not implement it.

## Frozen Theory State Interface

The future reduced Theory State interface is frozen as:

```text
z =
(
    y,
    w,
    g_R,
    c_R,
    g_F,
    c_F,
    g_T,
    c_T
)
```

where:

```text
y = Ego lateral coordinate
w = Ego lateral velocity
```

and:

```text
c_R = v_RO - v_E
c_F = v_E - v_FO
c_T = v_RT - v_E
```

Positive `c_R`, `c_F`, or `c_T` means the corresponding safety gap is closing.

The future architecture is:

```text
Physical Vehicle / Road State
        |
        v
Geometry and Theory Parameter Mapping
        |
        v
Reduced Theory State Builder
        |
        v
z = (y,w,g_R,c_R,g_F,c_F,g_T,c_T)
        |
        v
Frozen Theory Evaluators
```

The future Theory State Builder is an adapter between simulation state and analytical state.

It must not become the authoritative vehicle dynamics model.

## Theory scope protection

Software implementing the frozen theory must preserve the current reduced-model assumptions.

In particular, do not silently introduce into the frozen reduced evaluator:

```text
target-lane front vehicle FT
speed-dependent safety clearances
surrounding-vehicle acceleration
adversarial disturbances
full nonlinear vehicle dynamics
progressive w < 0
```

Such features would represent future model extensions and must be separated from the frozen reduced theory implementation.

## Implementation and governance boundary

This document freezes mappings and responsibilities only. It does not add
Scenario, TheoryStateBuilder, TheoryParameters, a Control struct, Dynamics,
Simulation Engine, CapabilityEvaluator, reserves, maneuver-freedom horizon,
`K_T`, or `K_O_abort` implementations. No MATLAB code or test is changed.

The physical bumper gaps used in simulation reporting and the safety-adjusted
theory gaps `g_R`, `g_F`, `g_T` are distinct quantities. The mapping subtracts
the corresponding required clearance exactly once. In particular, the rear
mappings are:

```text
g_R = x_E - x_RO - (L_E + L_RO)/2 - delta_R_clearance
g_T = x_E - x_RT - (L_E + L_RT)/2 - delta_T_clearance
```

This bridge does not alter analytical definitions or introduce new theory.
The data-model allowance of negative state values remains unchanged; the
restrictions of a future frozen reduced evaluator are separate from general
simulation-data validity. Surrounding-vehicle acceleration remains a broader
Phase 0 simulation requirement, but must not silently enter that evaluator.
Any extension to the frozen reduced model must be identified and kept separate.
No P0.2.3 development is part of P0.2.2b.
